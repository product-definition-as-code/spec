# Migrating v0.2.0/v1alpha1 to v0.3.0/v1alpha2

This is an explicit breaking migration. Keep the released v1alpha1 schema set and v0.2 conformance results available. Select v0.3.0/v1alpha2 only after migration and review; no missing-config default silently converts an old invocation.

1. Inventory baseline artifacts and every live Product Change. Resolve artifact identity from frontmatter, not directories. Stop and report missing, ambiguous or wrong-type Use Case targets; do not invent artifacts or drop unresolved relationships.
2. For each Business Rule `applies-to` Use Case target, add that Rule ID to the target UC's `governed-by` if absent. Preserve existing order and append missing Rule IDs in Unicode code-point order. Deduplicate the specific association. Remove those UC targets from the Rule, retaining Journey/Bounded Context scope. Remove the field if no broad targets remain. Never infer associations through bounded-context membership. Repeating the migration MUST make no additional changes.
3. Rebase live proposed artifacts against the migrated baseline, preserving both baseline and proposed relationship intent. Review and update their base revisions and pins after revalidation. Completed, rejected and superseded archives remain unchanged; they record the old accepted representation.
4. Change an existing `.product/config.yaml` version to `v1alpha2`; explicitly select the new pair when no config exists. Domain Lifecycle remains optional to author; existing inline verification remains supported. Do not manufacture lifecycle coverage or evidence.
5. Validate the full baseline and each live overlay. Review one-hop impact causes and write genuine unchanged judgments with current candidate/cause pins. Evidence is optional and must be selected explicitly by its adapter.
6. Verify consumer citations and review any staleness caused by migration. Do not automatically renew consumer or historical evidence digests: that would falsely claim re-verification. Fixture pins may be recomputed deliberately when preserving a fixture's intended current status.

Keep a migration commit for review and rollback. Rehearse against a copy, verify a second run is a no-op, and run both the new conformance cases and the pinned v0.2 suite with their respective schema/spec pair. Release qualification records exact implementation versions and every unexecuted case.

## Baseline migration helper

Install the pinned audit dependencies from `scripts/requirements.txt`. Run `python scripts/migrate-rule-governance.py <path-to-model>` to inspect the files that would change, then add `--write` to apply that reviewed baseline migration. The helper validates all UC targets before writing, retains broad scope and existing governance order, and appends missing rules in sorted order. It does not migrate active overlays, configuration, archives or consumer pins; complete steps 3–6 above explicitly. Frontmatter is reserialized while the body is retained. `python scripts/test-migration.py` exercises idempotence, unresolved/wrong-type targets and the no-inference rule.

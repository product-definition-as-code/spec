# Proposed synthetic intent — owner G1 review required

This is a benchmark fixture, not accepted real product knowledge. The human owner must approve or revise every decision below before G1 freeze and scoring. All four cohorts receive these same facts, examples, episode requests and predecessor history; treatment changes representation/governance and verification access only. There is no executable reference oracle in author materials. Stable identifiers identify prose decisions, not a formal language. The fixed [interface](INTERFACE.md) governs names and interchange.

## Domain and units (BOOK-DOMAIN)

One operation considers one reservation and a shared capacity pool. `used` counts integer capacity units already occupied by all confirmed reservations, including this reservation when CONFIRMED; `capacity` is the pool's integer capacity. REQUESTED consumes no units. Each confirmed reservation consumes exactly the episode's footprint (B0/B1: 1 unit; B2 onward: 3 units). These are indivisible units; no rounding or conversion of supplied values occurs. Capacity and used are already measured in the current episode's units. B2 changes each reservation's footprint, not the numerical meaning of one capacity unit. It does not migrate historical numeric states: predecessor evidence remains about its old model; new requests use states valid for the new footprint.

`days` is an externally supplied integer count of whole days until the reservation begins; zero is the start day. Subday time, time zones and elapsed time are outside this model. `due` is a trusted externally supplied eligibility flag for expiry; it is independent of days. There is no clock, timer, automatic transition, scheduling guarantee or inferred relationship between due and days. Operations are atomic and evaluated against a coherent snapshot; concurrent calls and persistent storage are outside scope.

## Total input and rejection (BOOK-INPUT)

The runtime input is a dictionary representing a JSON object. It must contain exactly the eleven interface keys, with no missing/extra keys. status, used, capacity, days, actor, owner, issuer and operation must be integers, excluding booleans, floats and strings; due, authenticated and editor must be booleans. Integers have mathematical precision, with no upper limit. status must be 0..3, operation 0..3; used, capacity, days, actor, owner and issuer must be nonnegative. used must not exceed capacity. A CONFIRMED state must have used at least the current footprint. Capacity zero is valid for REQUESTED and terminal states. No further history, owner existence or reachable-history constraint is imposed. Terminal states may coexist with any otherwise valid pool usage. Invalid input is always rejected before any business operation.

Every call returns exactly accepted, status, used and owner. accepted is boolean. Rejection, whether malformed input, invalid state, failed authorization or unmet guard, returns accepted=false and copies input status, used and owner exactly, without repairing them. If one of those keys is absent, its returned value is null. Invalid JSON values therefore may appear unchanged in these three rejection fields. The interface accepts dictionaries only; non-dictionary Python callers are outside its declared API. No error category or precedence is exposed. Unknown operations/statuses reject. Extra fields reject even if their values are otherwise harmless.

The SMT interface already types integers/booleans and has no missing/extra keys; its total relation covers every assignment of those sorts, including negative integers and out-of-range codes. Wrong runtime types/shape are runtime obligations, not an SMT proof claim. Rejects preserve state there as well.

## Identity assumptions and authorization (AUTH-TRUST, AUTH-RIGHTS)

actor and owner are stable opaque nonnegative identity numbers; equality means the same identity. The caller cannot write identity or role assertions in a real service: an external trusted authenticator supplies actor, issuer, authenticated and editor consistently. authenticated=true means identity verification succeeded; editor=true means that authenticator asserts a global trusted-editor role for this actor. The experiment assumes these assertions and tests decisions over them; it does not verify token cryptography, account existence, revocation, role issuance, network or authenticator correctness. owner is part of the trusted stored reservation snapshot. Even the owner or an editor must be authenticated by a trusted issuer. Unknown nonnegative issuer numbers are valid data but untrusted.

Trusted issuers are {0} through B3, and {0,1} from B4 onward, including A0. An editor assertion from an untrusted issuer grants nothing. CONFIRM and CANCEL allow either the reservation owner or a trusted editor. EXPIRE requires a trusted editor. EDIT requires a trusted editor through B6. In the independent A0 authorization contrast, EDIT permits either the owner or a trusted editor; every other rule is identical to B6. There is no administrator bypass. EDIT acknowledges authority to edit nonrepresented descriptive content; it changes none of this interface's state. This deliberately small operation makes the rights contrast observable without adding a semantic API or a new field.

## Booking operations and frame (BOOK-CONFIRM, BOOK-CANCEL, BOOK-EXPIRE, BOOK-EDIT)

These four paragraphs are stable direct use-case text. B4 changes AUTH-TRUST only: retain these paragraphs byte-identical and derive their authorization from AUTH-TRUST/AUTH-RIGHTS. An author's original direct use-case artifact must likewise remain byte-identical in B4 where the released artifact format permits that separation. Record any unavoidable representation exception before scoring.

CONFIRM: After BOOK-INPUT validation and AUTH-TRUST/AUTH-RIGHTS authorization, accept only from REQUESTED, with days no greater than the episode's maximum lead window and enough unused pool units for the episode's entire footprint. On acceptance set status to CONFIRMED and increase used by the footprint. Zero days and exactly the maximum lead window are included. due does not affect this operation.

CANCEL: After BOOK-INPUT validation and AUTH-TRUST/AUTH-RIGHTS authorization, accept from REQUESTED at any valid days, or from CONFIRMED when days is at least two. On acceptance set status to CANCELLED; release exactly the footprint only if the old status was CONFIRMED. There is no additional due condition. The two-day threshold is inclusive and unchanged throughout the experiment.

EXPIRE: After BOOK-INPUT validation and AUTH-TRUST/AUTH-RIGHTS authorization, accept only when due=true and the old status is among the episode's expiry source statuses. On acceptance set status to EXPIRED; release exactly the footprint only if the old status was CONFIRMED. There is no days threshold. Initially only CONFIRMED is eligible; B3 adds REQUESTED. No release occurs for REQUESTED.

EDIT: After BOOK-INPUT validation and AUTH-TRUST/AUTH-RIGHTS authorization, accept only from REQUESTED or CONFIRMED. On acceptance retain status and used. days and due add no guards. Terminal states reject every operation, including EDIT.

Every accepted operation preserves owner. It also preserves all unreturned inputs and all other reservations; only the selected reservation's status and its contribution to pool usage may change as stated. There is no transfer, creation, deletion, capacity adjustment, automatic release, repeated cancellation/expiry success or hidden write. Rejection preserves the complete state. Existing terminal state usage represents other reservations and must not be decremented.

## Independent artifact and public behaviour (AUDIT-RETENTION, SB-CAPACITY)

AUDIT-RETENTION: Retain audit records for seven whole days initially, changing to fourteen at B5. Record persistence/deletion is outside decide and Step; there is no audit input or output. This requirement has no dependency on any booking or authorization decision. It exists to test honest scope and evidence applicability without inventing an executable retention API.

SB-CAPACITY wording through B5: “A requested reservation with sufficient free units can be confirmed by an authorized caller within the lead window.” B6 wording: “Within the lead window, an authorized caller can confirm a requested reservation when sufficient units are free.” Both refer to BOOK-CONFIRM and its complete guards/effects; this example sentence is not an alternate complete contract. Meaning stays identical. Its byte change can stale a citation without invalidating the mathematical booking property. Never silently renew citation pins.

## Episode authority and review risks

B0 establishes the baseline. B1 changes the inclusive maximum CONFIRM lead window from 48 to 21 days. B2 changes footprint from 1 to 3 units and updates public examples. B3 adds REQUESTED as an expiry source and retains conditional release. B4 adds trusted issuer 1 while preserving direct use-case bytes. B5 changes only unrelated audit retention 7 to 14 days. B6 changes only SB-CAPACITY wording. A0 branches independently from B6, changes only EDIT rights to owner-or-editor, and must not be treated as a further booking change.

Owner review must explicitly accept: CONFIRMED-only occupancy; B2's changed footprint without state migration; the inclusive 0..lead CONFIRM window and two-day CANCEL cutoff; due's independence from days; arbitrary otherwise valid state snapshots; EDIT's state-preserving acknowledgement; immutable ownership; fail-closed malformed inputs with raw state echo/null for absent fields; trusted supplied identity/roles; terminal rejection; and independent audit retention. These are proposed synthetic policies rather than discoveries. Authors must flag contradictions or additional needed decisions and stop affected claims; they may not silently choose another policy.
